How does a file you save on your laptop show up on your phone a moment later?

One saved file, from the folder to the phone. The decision turns on sending only the blocks that changed.

Best for
  1. Finishing a deck on the trainStarted on the office laptop, finished on the phone. The file is already there, and nobody emailed it to themselves.
  2. Sending a client a folder too big to emailA designer shares a link instead of an attachment. The client opens it in a browser, with no account.
  3. Getting back a file you saved overThe good version went on Friday. Version history brings it back without asking anyone.

Less suited totwo people typing in the same document at once; Google Docs merges the keystrokes, Dropbox keeps a conflicted copy.

Who uses it
  • The freelancerWorks across a laptop and a phone. Wants the latest file wherever they are, without asking which copy is newest.
  • The small teamShares one folder per client. Wants everyone on the same version, and a way back when someone deletes the wrong thing.
  • The photographerMoves large files every week. Wants camera uploads off the phone and a link a client can open.
  • The IT adminPays for the team plan. Wants to see who has access, and to remove it the day someone leaves.

Part 1 · The folder

The folder: an ordinary folder, watched.

The desktop app asks the operating system to report every change inside one folder. Save a file there and the app hears about it. There is no upload button to press.

Source · Dropbox

PM angleNo button means no new habit: the product is a folder people already know how to use.

Part 2 · The blocks

The blocks: every file cut into 4 MB pieces.

The app splits each file into blocks of up to 4 MB. Edit a file in place and only the blocks that changed need to travel.

Source · Dropbox

PM angleBlock size is a product dial: smaller blocks send less after an edit, larger ones keep the list short.

Part 3 · The hashes

The hashes: a fingerprint for every block.

Each block is run through SHA 256 to give a short fingerprint. Two identical blocks get the same fingerprint, wherever they come from.

Source · Dropbox

PM angleThe fingerprint lets the server answer one cheap question: have I seen this block before?

Part 4 · The block store

The block store: each block kept once.

Blocks are stored by fingerprint, so the server asks only for the ones it lacks. Since 2016 most of them live in Magic Pocket, Dropbox’s own storage, built to move off Amazon S3.

Source · Dropbox

PM angleDeduplication is a feature and a margin at once: uploads finish sooner and the storage bill shrinks.

Part 5 · The file list

The file list: which blocks, in what order.

Metadata servers keep, for every file, its path, its version and the list of block fingerprints that make it. Other devices read the new list and fetch only the blocks they lack.

Source · Dropbox

PM angleThe list is the truth. If it and the blocks ever disagree, people lose work.

  1. 1YouSave the file; the app sees the folder change.on your laptop
    The save is the whole interface

    Nobody presses sync, so nobody knows when it starts. The PM owns the small icon that says it is done, because that icon is the only proof people get. An icon that says done too early is worse than a slow one.

    time from save to the green tick · saves that never upload
  2. 2The appCuts it into blocks and fingerprints each one.4 MB, one hash each
    Work on the laptop is work you do not pay for

    Cutting and hashing run on the customer’s machine, which keeps servers cheap and puts the cost on battery and fans. A PM watches the client’s footprint as closely as the server bill, because a hot laptop gets the app uninstalled.

    client CPU during sync · uninstalls after a large first sync
  3. 3ServerSays which fingerprints it lacks; only those blocks upload.the changed blocks
    Bytes saved is the number behind the promise

    Every block the server already has is an upload that never happens. That makes the share of blocks skipped both the speed story for users and the margin story for finance. They pull the same way, which is rare.

    blocks skipped per upload · bytes uploaded per edit
  4. 4File listRecords the new version as a list of fingerprints.a new version
    When two saves collide, keep both

    If a laptop and a phone change the same file before either hears of the other, Dropbox keeps one and saves the other as a conflicted copy. Nothing is lost, but someone has to merge by hand. The PM decides how loudly to say so.

    conflicted copies per 1,000 edits · copies left unmerged
  5. 5Your phoneIs told there is news, then fetches only what it lacks.moments later
    Moments later has to be measured on the phone

    The server knows when it sent the news, not when someone could open the file. A PM wants the time from save on one device to open on another, in the field, split by network and file size.

    save to available elsewhere · notifications that arrive late

Only fingerprints travel first. A block moves only when the server has never seen it.

Fig. 3 · The system behind one saved file
  1. Your laptop

    Notices the save and cuts the file into blocks.

    • Sync engineNucleus, rewritten in Rust and shipped in 2020, watches the folder, hashes blocks and keeps its own copy of the file list.
    The client is the product

    Most of what people feel happens on their own machine: the watching, the hashing, the icon. Every operating system update can break it, so the PM plans releases around Windows and macOS as much as around features.

    sync errors per 1,000 clients · clients on old versions
  2. Dropbox’s servers

    A catalogue of fingerprints and a warehouse of blocks.

    • Metadata serversHold every file’s path, version and list of block fingerprints: the record of what is true.
    • Block storageMagic Pocket keeps each block once, copied across data centres, after the move off Amazon S3 in 2016.
    • NotificationsHold an open request from each device and answer it the moment something in its folders changes.
    Two stores, one truth

    Blocks are cheap to keep and hard to lose; the file list is small and must never be wrong. Outages people remember are list outages, so the PM treats metadata speed and correctness as the product, and storage as the cost line.

    metadata write latency · storage cost per paying user
  3. Your phone

    Hears the news and fetches what it lacks.

    • Fetch on openLists every file at once but downloads one only when it is opened, unless it is marked for offline use.
    The phone is a window, not a mirror

    A phone cannot hold everything, so it holds the list and fetches on demand. That makes time to open the phone’s real speed metric, and offline files the feature people miss only on a plane.

    time to open a file · files marked for offline use
In plain words

Like a library that keeps every page once. Revise a book and you send only the new pages and an updated contents list. Every other branch is told, reads the list and collects the pages it is missing.

Design choices, and what they cost
  1. Cut files into blocksSmall edits make small uploads. The cost: a client that has to hash and track every block on every operating system.
  2. Store each block onceIdentical blocks are uploaded and kept once. The cost: one block can sit inside many files, so checks on it have to be strict.
  3. Keep both on a clashTwo edits to one file both survive as a conflicted copy. The cost: people merge by hand.

How it grew
The spike
From 100,000 registered users in September 2008 to 4 million by January 2010, with no paid marketing doing the work.
What drove it
A referral offer: extra free space for you and the friend you invite. Drew Houston said it lifted sign ups by 60% for good, and in April 2010 users sent 2.8 million invites in 30 days.
How they iterated
Search ads cost more to win a customer than the $99 a year plan brought in, so they stopped buying them and built invites into sign up and the first run of the app. Later, paid teams with admin controls became the business.

What sets it apart
The algorithm · Hash each block
In plain words
A library that checks each page against the ones it already holds, and files only the new ones.
The promise is the right file, everywhere

People are promised that what they saved is what they will open elsewhere. A fingerprint clash is not the risk; a file that looks synced and is not is. The PM’s job is an icon that never says done before it is.

files shown as synced that fail to open · support tickets about missing files
It optimises
Bytes sent and kept: a small edit uploads the changed blocks, not the whole file.
Speed and margin, measured on one edit

Track bytes uploaded per edit and time from save to available elsewhere; both fall when more blocks are skipped. The pull comes from metadata: more, smaller blocks mean more fingerprints to store and check for every file.

bytes uploaded per edit · fingerprints stored per file
The dial
Block size: smaller blocks send less after an edit but mean more fingerprints to track.
Sync engineering turns it, the PM sets the bar

Block size lives with the sync team, but the PM says which matters more: a quick upload on a slow connection or a cheaper list. Test it on real edit patterns, by file type, with a slice of clients against a holdout.

upload time by file type · metadata size per file
Same idea
Git, which names every version of a file by its hash.
Name things by what they contain

Git and Dropbox both store content under its own fingerprint, so a copy is never stored twice and any change is easy to spot. What carries over for a PM: once content names itself, history and version restore come almost free.

versions restored a week · storage saved by deduplication
The edge
Block level sync that works the same on every computer and phone.
  • Files are cut into 4 MB blocks and each is named by its SHA 256 fingerprint, so a block already stored is never uploaded again.
  • One folder behaves the same on Windows, macOS, Linux, iPhone and Android, which no bundled rival aims for.
  • Google Drive and OneDrive come free with Workspace and Microsoft 365; iCloud Drive comes with an Apple device. Dropbox has to be chosen.

The PM lens

“How would you measure the success of Dropbox?”

Product sense and metrics case · a common practice prompt
What the round tests

Whether you separate the free habit from the paid business.

  1. Start from the job.People hire it to have the right file wherever they are. So the north star is files opened on a second device, not storage used.
  2. Measure trust in sync.Time from save to available elsewhere, and conflicted copies per 1,000 edits. A file that silently fails to sync costs more than a slow one.
  3. Follow the path to paying.Free users hit the limit, invite colleagues, share a folder. Track who crosses into a team, because teams carry the revenue.
If this goes wrong

Chase storage used and you reward hoarding, while the people who pay want the right version, found fast.

The decision inside

Send only what changed.

  1. StopYou save on the laptop and the phone already has it.More than 700 million registered accounts.
  2. NoticeMost saves change a small part of a file, and many files already exist on the servers.One fingerprint for every 4 MB block.
  3. TradeoffUpload whole files and keep the app simple, or cut and hash on every computer.A simple client, or a smart one.
  4. DecideCut every file into 4 MB blocks, fingerprint each one and upload only blocks the server has never seen; when two edits collide, keep both.What it cost: a desktop app that has to be right on every operating system.
